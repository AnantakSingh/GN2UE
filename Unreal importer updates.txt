Done — the no-MCP importer works end to end. A headless UE 5.8 run rebuilt the whole SpineTree effect from spinetree.gnue.json: 12 nodes, 11/11 edges, both spawner meshes assigned, and every setting verified by re-loading the saved asset (duplicate iterations, wander bounds, sampler counts with seed-from-index, cube scale on the tangent axis, $Density noise + ≤0.35 filter, leaf rotators, uniform 0.6 scale — all matching the hand-built graph).

What was built
import_gnue.py — the importer, using only UE's built-in Python scripting. It's family-dispatching (reads family: static_scatter and maps curve.random_walk / scatter.on_curve blocks to PCG node chains), evaluates descriptor expressions (max, add, segment_overlap), imports the FBX meshes, creates and assigns a two-sided leaf material (closing gap #5 for the imported copy), and saves everything non-destructively under /Game/GNueImport/SpineTreeGN/ — your hand-built /Game/SpineTree/ is untouched.
run_import.ps1 — headless runner (UnrealEditor-Cmd -run=pythonscript), works with the editor closed, CI-able. It judges success by the script's own result line because the MCP toolset's port-8000 bind failure (your interactive editor holds the port) otherwise forces exit code 1.
ue_importer/README.md — usage plus the 5.8 API notes; export/README.md updated (gap #6 marked done — I added PCG and PythonScriptPlugin to GNtoUE.uproject, which cooking needed anyway).
To see it: open the editor, drop a PCG Volume in a level, set its graph to /Game/GNueImport/SpineTreeGN/PCG_SpineTreeGN.

Two findings worth knowing
Your UE project already vendors a third-party "GeometryNodesBridge" plugin (from lassiiter/blender-geometry-nodes-to-unreal, currently disabled in the uproject, with an installer bat). It's a live-sync/bake bridge — a genuinely different architecture from your parametric-descriptor approach. Worth a look before designing your client plugins, both as prior art and to keep the two clearly separate.
The one thing 5.8 Python cannot do is declare graph parameters (PCGGraphParametersHelpers has only get/set). So gap #1 (param declaration + wiring) is the concrete reason the eventual UE client plugin wants a small C++ module; everything else the plugin needs is already proven in script form. The 5.8 API quirks that cost debugging time (edge API, in-place mesh selector, protected selector fields, exit-code trap) are saved to memory so they don't get rediscovered.
